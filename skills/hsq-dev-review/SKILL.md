# 审查、审计与反馈

## 变更审查

以用户指定基线为准。默认审查工作区相对 HEAD 的 staged、unstaged、untracked；没有改动就报告，不自动回退最后一次提交。分支/PR 审查确定 base/head 或 merge-base，工作区和提交范围不要混淆。

读 diff 后继续读关联调用方、被调用函数、测试与相关 README，追踪输入→存储/状态→输出。签名、返回值或行为变化检查全部消费者；查仓库运行/部署配置的真实负载并说明假设，不凭想象的超大规模要求重构。

分两条轴核查：需求/Spec 验收是否满足；工程质量是否符合项目规则。优先级：正确性 → 安全/数据保护 → 预期负载下的并发和资源 → 风险逻辑测试 → 性能 → 精简。

重点检查：功能回归、敏感信息、校验/注入、错误吞没、事务/写顺序、兼容、竞态、幂等、重复工作、无界状态、N+1、配置契约、测试隔离和范围混杂。测试应执行行为；检查干净 checkout、被忽略产物和生成依赖，不能只匹配源码。

精简发现必须有当前需求依据：死代码、无消费者选项、可复用 helper、仅转发包装或必须一起变更的复制逻辑。按职责拆分，不按行数拆函数。声明“无用”前搜索字符串、动态引用、配置、fixtures 和测试。已记录限制的 shortcut 只有预期负载/需求已超出限制才构成问题。

## 发现与报告

每条问题必须有具体触发输入/情境、代码证据和实际后果；无具体案例不报猜测性问题。重新核对相关行、调用者和可达性，提出最小可行修复。先按严重度列可操作问题，附文件行号及验收/质量类别；每条简述触发、影响和建议。可用“必须修复 / 应修复 / 可选改善”区分等级，不把风格喜好当阻塞。

无问题时明确说明，并列检查范围、未验证项和残余风险。仅报告，不擅自修改。

## 全仓审计与债务

全仓审计先读 README、部署/构建配置、依赖、入口和测试，绘制主要数据流，优先深入鉴权、金额、用户输入、数据写入、后台任务和跨进程共享状态。大仓库按风险深入，报告未读范围，不能声称穷尽。

仅当用户要债务清单时，搜索版本控制源码中的 `shortcut:` 和旧 `ponytail:` 注释，排除依赖、构建产物及非债务用法。按文件列限制、升级触发条件和方向；缺触发标记为 no-trigger。读取报告授权不包含持久化债务文件或修复。

## 收到评审反馈

先完整阅读、理解、对照代码事实验证，再决定接受或有证据反驳；不盲从评审者，也不以奉承代替核查。核查当前版本、平台、消费者、兼容和已有决定；建议加功能先找实际需求。关联且不明确的意见先澄清，独立且已获授权的工作可继续。涉及核心 Spec 实质冲突按停止规则处理。

用户授权修复后按阻塞问题、简单修复、复杂修复处理，逐项验证再做相关回归；只审查的请求不等于修复授权。外部回帖/发送必须另有明确授权。
