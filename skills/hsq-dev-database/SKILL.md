# 数据库与 API

## 个人 SQL 约束

- 未明确同意不使用窗口函数。拟用时先说明必要性、数据库/版本兼容性、性能影响和替代方案，等待确认；可选择符合目标的非窗口方案继续。
- 未明确确认不创建唯一索引、不新增表字段。先说明业务约束、影响范围、存量重复/空值及兼容、迁移和回滚方式、替代方案。分别核对授权，批准一项不覆盖另一项；笼统“优化”“实现”“自行选择”不构成这些操作的同意。直接指定该字段、唯一索引或窗口函数的明确指令可作为相应授权，不重复询问。
- 这些限制同样适用于生成 SQL、migration、ORM schema 或其他间接实现；不能以未执行数据库为理由先写入被禁止的变更。
- 生产写入、破坏性去重、锁表或高风险迁移另受核心授权规则约束；源码修改授权不自动包含线上执行。

## 查询设计与证据

同时验证结果正确性和性能。结合真实数据规模检查过滤、索引利用、扫描范围、Join、排序、聚合、分页、返回量和数据库往返。性能敏感改动需要执行计划或等价证据；只有静态推测时明确剩余风险与验证方式，不声称性能已验证。

减少高耗时 SQL、不必要重复查询、N+1 和依赖前序结果的线性查询链。在保证语义、一致性、可维护性和性能前提下，优先独立执行、批量获取或并行组织；避免串行延迟累积。独立优先不等于强行拆分，也不等于追求最少 SQL；按数据量、索引、锁、网络往返、事务和执行计划取舍，不能强合并成复杂大查询。

修改 API 查询逻辑时说明查询次数、依赖、批量边界、失败语义与一致性要求；检查快照/事务语义、权限过滤及并发。用执行计划、耗时、扫描行数或接口同条件前后指标验证，并验证边界/旧数据和错误路径。
