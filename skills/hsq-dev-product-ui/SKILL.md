# 业务界面与交互

让业务用户看懂当前情况、找到下一步操作并及时看到结果。沿用项目设计系统和已确认布局；本工作流补充个人产品偏好，外部 UI 技能提供专业方法，等价步骤执行一次。工程实现、诊断、交付仍使用相应工作流，不以 UI 任务绕过常驻授权和浏览器规则。

## 信息围绕用户任务

- 先根据现有代码、截图、设计稿和用户材料理解实际使用流程，确认用户在此处需要理解、决定或操作什么；不为读取界面自行启动浏览器。
- 用业务名称、任务概览和可操作的错误提示替代无意义的内部编码、原始调度提示词及底层异常。普通用户不应为完成业务先理解 env、内部 agent 名称或认证字段；专业配置页可保留必要术语并解释用途。
- 错误提示说明发生了什么、用户能怎么处理；技术诊断信息放到日志或适合的详情，不把实现细节当产品内容。
- 保留有助于判断的信息，弱化次要信息；不能为“精简”删掉必要状态或操作说明。

## 按阶段选择原型

用户明确要求“先看 HTML／图片原型”时，先交付可查看的局部原型，这仅授权原型产物，不包含修改正式界面。实际 Harness 计划模式仍保持只读。只讨论设计而未要求产物时，不自行写原型文件。

已获实现授权且有明显未定的布局或交互选择时，可用范围内的轻量原型帮助判断；目标明确的小文案、间距、局部样式或既定方案直接处理，不机械增加原型或确认环节。

- 原型聚焦需要判断的组件或区域，不扩成无关整站；需要判断点击、展开等交互时提供相应可操作状态，静态图不能证明交互有效。
- 使用长标题、多位数字、加载或展开状态等足以影响决定的样例；实现遵循已经认可的原型，不自行替换设计。
- 请求生成或查看原型不自动授权浏览器验证、截图或安装工具。遵守常驻浏览器门槛；没有明确浏览器请求时不调用、不建议或询问浏览器验证。

## 操作与反馈对应

- 在用户发现问题的位置提供合理入口，如待更新状态旁的更新操作、子任务卡片到详情的跳转。
- 点击后及时反馈已接收、处理中或失败；把请求接收与实际成功区分清楚，不能乐观显示未经确认的完成结果。
- 审批、取消、停止等动作生效后更新相应按钮和状态，不等整个任务结束才刷新；失败时回滚或说明当前状态。
- 同类操作名称与行为保持一致。悬浮出现的次要按钮兼顾键盘和触屏访问，不以隐藏牺牲可发现性。

## 内容与状态适配

根据组件实际需要检查空、加载、正常、失败、不可操作、长文本、多位数字、展开/收起及较窄窗口。布局用合适的换行、截断和弹性空间承载真实内容，不用固定字数或固定列数掩盖问题。

弹框大小、输入区域和主次按钮围绕使用任务；复用现有组件、状态标识和排版规则，避免局部优化破坏全局一致性。涉及实时数据时按 implement 的关联路径核对即时反馈、刷新后历史、列表与详情；状态事实冲突先由 diagnose 定位，不靠界面兜底掩盖。

## 验证与交付

遵循 implement 的风险验证和用户本次限制。用户说明热更新后自行查看，或要求不编译、不截图时照做，说明尚未验证的视觉行为；没有浏览器授权时完成适用的非浏览器检查，不把它等同于视觉效果已验证。

只交付原型时说明展示范围与模拟行为，不声称后端功能已经实现。正式界面实现完成后使用 deliver，说明改善的使用问题、关键状态及实际检查结果。
