# 设计与计划

## 从结果到最小模型

先读现有项目和用户材料，明确用户要获得的可观察结果、边界和验收条件。不要把页面、字段、接口或现有实现误当需求本身。区分业务事实、硬约束、不变量、历史惯例和假设；验证会改变设计的关键假设。

核实 Spec 关于现有行为、数据来源、状态归属、接口、依赖和根因的关键陈述。实质冲突遵循常驻核心的停止规则；普通命名或组织差异不阻塞。设计讨论授权不包含创建产品代码、安装依赖或修改配置。

从事实推导最小领域模型、权威数据源、状态归属、转换、失败语义和接口，再映射到现有架构。说明为何这些机制足够、为何更少不够。优先复用，避免为未来需求添加配置、包装和抽象。

先通过检查解决可发现事实；只向用户询问会改变目标、验收或高风险取舍的关键未知。存在真正不同的方案时简述收益、成本及推荐理由。需求与授权已明确时给出简短方案、风险和验证方式后自主推进；不机械添加方案选型、设计、计划三轮审批。实际计划模式遵守 Harness 的只读及 exit_plan_mode 规则。

## 可执行计划

小改动无需计划文件。多步骤任务按可独立交付和验证的行为拆分，不按文件或机械的 RED/GREEN 操作拆为多个审批任务。每项说明：目标、范围/文件、依赖、接口及状态变化、验收、相关验证命令与预期结果。把项目全局约束放在共同位置，避免逐任务重复。

验收必须既覆盖需求，又覆盖相关失败路径和兼容性，不能只写“测试通过”。普通任务使用 Todo 连续执行；只有显式逐步模式才逐项等待确认。计划中的 Git 操作不构成授权。

## 执行与委派

默认主 Agent 实施。独立子系统、独立调查或较长计划可用自包含子 Agent；说明为什么收益值得启动成本。相互依赖的任务按顺序处理；只并行无共享写入和资源冲突的工作，固定文件/职责所有者。

委派提供：工作目录、需求/Spec、输入与依赖、负责范围、接口、验收、验证方式、已知证据、只读/SQL/Git/逐步授权限制、Spec 实质冲突上报要求。不要默认传整段会话给独立评审者。子 Agent 报告应包含改动、实际检查、问题、未确认事项；不能把其自报成功当作验证。

复杂或高风险交付使用独立审查，分别给出需求符合度和代码质量判断；子 Agent 执行长计划时在独立任务交付点审查，最后检查组合行为。普通小改动不为仪式启动多轮审查。无子 Agent 时自行核查并准确说明限制。

长任务优先使用现有 Todo/计划。只有它们不足以跨压缩恢复时增加简短记录：当前任务、已完成证据及适用代码范围、决定和理由、授权、剩余风险、下一步。恢复先读记录；不重复从头调查，也不以记录覆盖新证据。
