# 交付总结

先核对验收条件、实际 diff 和相关验证；不能只凭测试通过认定全部需求满足，也不能仅信子 Agent 报告。复用仍适用于当前代码和环境的检查，不为结尾机械重跑；最后改动使证据失效则补查。报告实际状态，不把未运行检查写成成功。

按以下信息顺序组织，简单改动两三个短段即可；较大改动可用三个短小部分：

1. **重要影响**：用户/业务行为先，其次接口、数据、配置与兼容，再其次架构、性能和维护性。明确现在有什么可观察变化。
2. **核心逻辑**：目标或修改前问题，以及实现目标的关键数据流、状态变化和机制；Bug 指明根因、恢复的不变量和修复方式。
3. **验证与注意事项**：实际执行的关键命令/场景及结果；配置要求、兼容、迁移、未验证范围和剩余风险。无对应事项可省略，不编造“无风险”。

合并同一行为的相关改动，不按文件、函数或操作时间线复述；避免“完成优化”等空泛结论，不倾倒长日志和辅助变量细节。重大兼容、迁移、配置和残余风险不能为简短省略。性能结论需同条件基线和后测；没有证据明确说未知。

交付前按相关性核对：其他功能/tool/消费者/租户/环境；旧用户、数据、配置、默认及创建/更新语义；并发、重复/乱序、重试、取消与刷新恢复；行为、失败和回归；相邻同根因候选；是否需更新契约文档或 Wiki。只报告证实的候选，不扩大修复范围。

配置、部署或发版约定发生实际变化时，更新已有 spec、Wiki 或版本文档的对应位置，不为每个小改动另建文档。说明相关配置的默认值、覆盖优先级、作用域和生效方式；个人开发覆盖不要变成公共默认。交代本次是否需要重建、重启、迁移或无额外操作，只写已确认事实。发版请求核对版本号、实际变更和升级步骤，不擅自发布或递增版本。

迁移说明按真实历史部署核对并行开发、重复启动和跨版本升级；不能用吞掉所有数据库错误宣称幂等，已有结构仍应符合预期。数据库变更仍遵守 database 的专门授权，代码交付不代表已执行线上迁移。

用户明确要求浏览器验证或未做浏览器检查构成重要验收限制时，如实说明执行情况，不能暗示已跑；未要求时不例行询问、建议补跑或把浏览器验证变成后续待办。只诊断/审查/设计时使用相应报告格式，无需套功能交付模板。Git 已获授权执行时补充分支、提交、合并或推送结果。
