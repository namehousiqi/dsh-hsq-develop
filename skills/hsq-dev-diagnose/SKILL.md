# 诊断与性能

## 建立可证伪的因果链

1. 定义可观察预期、实际行为和触发条件；完整阅读错误、堆栈、路径、错误码及相关近期改动。报错位置不是根因证据。
2. 区分已验证事实、业务硬约束、必须保持的不变量、历史惯例、待证假设。Spec 声称的当前行为或根因也必须验证；实质冲突遵循核心停止规则。
3. 尽量建立最小稳定复现；无法复现则保留观测证据、限制和下一步，不靠猜测补丁。对照相近的正常路径及版本、配置、依赖差异。
4. 沿输入、控制流、状态转换、事件时序、依赖和持久化反向追踪，找到最早被破坏的不变量。跨组件时检查输入输出和配置传播，只采集脱敏证据，不能回显秘密。
5. 形成“触发条件 → 首个违规点 → 状态/数据传播 → 用户可见症状”，每个关键环节有可证伪检查。区分直接根因、放大因素、相关风险和无关现象；区分真实丢数据与 UI 未显示、慢接口与调用方重复工作。
6. 一次验证一个主要假设，用最小实验隔离原因。没有新证据而连续失败时回到模型、责任归属和工作假设，不叠补丁；第三次失败前重新审视架构并报告已排除因素。

## 修复边界

只要求诊断时不修改源码、配置、文档、业务数据，不重启/部署，也不为插日志而写入。输出结论和确定程度、证据、因果链、影响范围、修复边界与未确认事项。

用户授权修复后加载 hsq-dev-implement。优先把修复放在能够恢复不变量的最低稳定责任边界；只有证明该处不能修改才采用上层补偿并说明局限。检查函数全部调用方及共享路径，不用固定延时、无界重试、扩大查询或字符串猜测掩盖错误。用回归行为证明修复。

异步/状态问题按相关性检查重复订阅、丢失/重复/乱序事件、重试、幂等、取消、重连、刷新恢复和持久化/UI 一致性。

## 性能

先选响应时间、吞吐、内存、渲染耗时/帧预算等指标和真实或接近真实数据规模，记录基线及环境。定位重复扫描、序列化、I/O、锁、缓存、重复请求及重渲染；用隔离实验验证主因，再做最小优化。同条件复测并报告前后数值。无可靠基线时只报告假设与测量计划，不声称更快。SQL/API 同时加载 hsq-dev-database。
