# 诊断与性能

## 任务目标与推进

诊断交付的是能够解释现场的因果机制及证据，不是最先找到的可疑代码或修复建议。用户问原因、根源或深入研究时，默认自主完成相关只读调查；不需要用户反复说“继续查”。先概括症状、范围和待验证问题，随调查更新，不把首次猜测写成结论。

“最小改动”约束修复规模，不限制必要调查深度；“简短”约束进度和表述，不降低证据要求。读完一个文件、找到一条异常日志、现有测试全绿或提供下一步建议都不是完成标准。若仍有会改变结论且可执行的相关检查，继续执行；下一步建议用于确实无法在当前授权和环境完成的工作。

## 调查循环

1. **锚定现场。** 记录可观察预期、实际、触发条件、首次出现/频率、受影响与正常样本。确认源码与部署版本、配置、环境、数据规模和时间线；现场不可用时注明分析仅适用于所读版本。只采集必要且脱敏的证据，不回显凭据、秘密或无关用户数据。已有有效证据复用，不机械重查。
2. **画出实际路径。** 从请求/事件入口追到状态归属、持久化、输出和 UI，再从异常反向追至最早破坏不变量的位置。读关键函数的调用方、被调用方、配置来源和相关测试；不能只读报错函数。跨进程核对边界两侧的输入输出及传递身份/上下文。区分事实、硬约束、惯例和假设。
3. **建立竞争解释。** 围绕现象记录有根据的候选原因、支持/反对证据、能区分它们的检查。优先验证既能解释失败又能解释正常样本的机制。不为了凑数量编造假设；简单确定错误不要求形式化假设表。
4. **主动找反例。** 对当前最强解释问“若它为真，还应该看到什么？什么结果会推翻它？”选择最小复现、正常/失败对照、隔离变量、实际配置、边界输入或日志时序检查。先解释实验将区分什么，再运行并读取完整结果；代码可达性不等于现场确已触发。
5. **沿证据继续深入。** 实验否定假设则更新模型；只证明“这里为空/超时/重复”时继续追问该状态由谁、何时、在什么条件下形成，以及为何现有保护没有生效。查上游写入、生命周期、身份/租户隔离、取消/重试、缓存失效和版本差异中相关的路径。不是无止境追溯历史，而是找到能解释触发条件、症状和正常边界的最早稳定责任点。
6. **验证因果与边界。** 形成“触发条件 → 首个违规点 → 状态/数据传播 → 症状”。在授权内用隔离输入/状态对照验证机制和关键预测，检查主要竞争解释。无需先改产品代码才能验证；有修复授权再通过回归验证修复。单次 patch 奏效也不能独自证明根因。

多轮调查保留短记录：当前问题、事实/假设、已排除解释、实验结果、待证关键链路与下一项检查，优先复用 Todo。多个独立子系统或暂时卡住时，先由主 Agent 调整假设与取证方法，不自动委派；只有达到常驻核心的委派门槛才启动自包含只读调查或独立反证。达到门槛并委派后，协调者核验发现，不能以多 Agent 投票代替证据。没有新证据的重复搜索不算进展，第三次同类无效尝试前重审假设、实验和责任边界。

## 外部机制与运行证据

涉及第三方库、框架、数据库或协议而本地代码不能确定语义时，先查锁定版本、实际依赖源码和官方文档/源码/issue；研究必须回答当前因果链的具体缺口，不能把搜索结果当现场证据。记录来源、版本和适用条件。搜索只是可用工具，不以未开放 research 技能为由停止必要研究。

跨本地/线上问题只使用已授权的只读现场入口；源码版本不能推定线上版本。无权限或材料时先完成可用本地证据，再具体说明缺哪一份日志/版本/输入会区分什么，不能笼统要求用户“再提供信息”。

## 完成门槛

- **根因已确认**：机制与触发条件有证据，关键传播环节闭合，有复现/隔离对照或同等强度的运行证据，主要竞争解释已检查；说明受影响范围及不触发的条件。
- **高可信解释，现场待核实**：源码和实验支持机制，但缺部署版本、真实输入或关键现场证据。分开说明“机制已复现”和“该次现场是否由此触发”。
- **尚未确定/受阻**：关键环节仍缺证据。列出已排除项、缺口、具体阻碍及最小解阻动作，不把最可能解释包装成已确认。

可结束于上述证据门槛、真正无法执行的关键检查、用户限定时间/范围或要求停止。报告必须区分正常调查进展、需要额外授权、环境缺失和真正无路可查。仍能在既有范围调查时不以“只读”“暂未复现”“建议再查”为理由提前交付。证据充分后及时收尾，不为显得深入扩成无关全仓审计。

报告先给结论与确定程度，再给触发/因果链、代码和运行证据、竞争解释的核查、影响与修复责任边界、剩余缺口。保留足以复核的文件行号、场景/命令及关键结果；不以“缓存问题”“竞态”或长日志代替机制。

## 权限与修复边界

只诊断时不写产品源码、配置、文档、业务数据，不重启/部署，也不为插日志而写入。可在无持久写入、外部副作用的隔离内存环境做实验；测试命令先检查是否写快照、数据库、缓存或发送请求。调查记录使用会话/Todo；需要文件型临时复现或额外现场权限时具体说明并确认，继续不依赖它的只读工作。

文档/Spec 根因只是待证假设。关键前提与代码存在实质冲突时仍停止实施、报告冲突并等待决定，但可继续有助于判断的只读取证，不能把发现冲突当作诊断已完成。

授权修复后加载 hsq-dev-implement。在恢复不变量的最低稳定责任边界修复，只有证明该处不可改才做上层补偿并说明局限；不用固定延时、无界重试、扩大查询或字符串猜测掩盖错误。

异步/状态故障按相关性检查重复订阅、事件丢失/重复/乱序、幂等、取消、重连、刷新恢复与持久化/UI 一致性；区分真实丢数据与 UI 未显示、慢接口与调用方重复工作、直接根因与放大因素。

先明确谁执行、谁产生事实、谁持久化、谁展示，再比较实时事件消费与历史加载。正常等待审批不能先被判为失败；展示级兜底不能成为权威状态，或让不同页面各自猜测结果。若界面错误只是结果，继续追最早错误写入或转换的位置。

必须可靠的系统状态不能仅依赖模型一定调用某个工具、更新提示词中的字段或输出特定自然语言；只有存在可验证的机制保障时，才能把模型动作纳入可靠状态链。修复时恢复已确认的状态归属和转换机制。相关列表/详情、主子任务和刷新路径的实现验收见 hsq-dev-implement，不另起重复检查流程。

## 性能

先明确响应时间、吞吐、内存或帧预算等指标，在真实/近真实规模记录基线和环境。定位重复扫描、序列化、I/O、锁、缓存、重复请求与渲染；隔离实验验证主因，同条件复测。无可靠测量只报告假设与计划，不能称“已优化”。SQL/API 同时加载 hsq-dev-database。
